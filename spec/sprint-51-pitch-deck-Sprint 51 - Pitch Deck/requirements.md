## Requisitos funcionales

R1. La presentación explica problema, usuario, solución, flujo de datos, acción temprana, demo, arquitectura, limitaciones y futuro mediante una narrativa coherente para el jurado.
R2. La presentación usa capturas del build final y cada captura identifica la vista o interacción que demuestra.
R3. Toda cifra simulada, experimental o dependiente de un corte temporal está etiquetada de forma visible y no se presenta como impacto observado.
R4. La arquitectura muestra Google Earth Engine, pipeline de señales, materialización/cache, API y dashboard con exportaciones, de acuerdo con la implementación vigente.
R5. Existen una versión editable `submission/deck/mwangaza-pitch-deck.pptx` y una versión exportada `submission/deck/mwangaza-pitch-deck.pdf` con el mismo contenido.
R6. El guion configura una duración objetivo de 5 minutos, asigna tiempo a cada slide y suma como máximo 300 segundos.
R7. La demostración principal conduce al evaluador desde la propuesta de valor hasta la capa `Persistent episodes` y el detalle ADM1; también documenta un fallback con capturas si falla la consulta en vivo.
R8. El deck diferencia claramente observación actual, referencia histórica y predicción ML experimental, e incluye las limitaciones de no predecir inicio exacto, duración exacta ni impacto humano.
R9. El entregable incluye fuentes o procedencia para las cifras técnicas y conserva el corte temporal de los datos mostrados.
